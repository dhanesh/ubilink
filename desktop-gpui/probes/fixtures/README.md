# Probe fixtures

Committed test data Phase 1's views and probes load through the automation
channel's `load_fixture {kind, path}` verb (`desktop-gpui/src/automation/protocol.rs`,
`crate::fixtures::path`) or through a scenario's `setup.files`/`setup.fixtures`
(`desktop-gpui/probes/README.md`). None of this is consumed by `desktop-gpui/src`
yet — Phase 1's views are the first readers — so this file is the schema contract
Phase 1 implementers build their consuming code against. Read it before writing a
view that reads one of these.

`python3 scripts/probe.py fixtures --check` validates every file below against the
shape documented here (stdlib only). `python3 scripts/probe.py fixtures --generate`
regenerates `graph-5000.json` deterministically; `--check` fails if the committed
file differs from a fresh run (so a hand edit can never silently drift from the
generator).

## Graph JSON (`graph-*.json`)

Every `graph-*.json` file is ubilink-core's own export/import JSON
(`core/src/graph.rs`, `LinkGraph::export_json`/`import_json`), schema
`"ubilink.graph.v3"` — the same shape `export_json` writes and `import_json` reads,
so these fixtures load through the real core import path, not a probe-only parser:

```json
{
  "schema": "ubilink.graph.v3",
  "resources": [
    { "guid": "<unique string>", "name": "<title>", "uri": "<unique uri>",
      "created_at": <integer ms, or null>, "path": "<optional>" }
  ],
  "links": [
    { "a": "<resource guid>", "b": "<resource guid>", "created_at": <integer ms, or null> }
  ]
}
```

- `resources[].guid` only has to be unique within the file (`import_json` stores it
  verbatim; it need not be a real UUID the way `LinkGraph::new_guid()` makes one).
- `links[].a`/`b` reference resources **by guid** (v3; `import_json` also still
  accepts the legacy `v1`/`v2` schemas for back-compat, but every fixture here is v3).
- `created_at` on a *link* is the backlink's timestamp — what recency ordering (R3)
  sorts on. `created_at` on a *resource* is its capture time.
- A scenario puts a graph fixture into an instance with `setup.graph` or the
  `seed_graph` step (`desktop-gpui/probes/README.md`), which write the instance's
  `ubilink-graph.sqlite` exactly as the core's `import_json` would, so the Phase 1
  scenarios need no `graph_dir` fixture plumbing in the app. It is read back with
  the `graph` step (its `export:` option reads an exported JSON).
  `export_path`/`import_path` name a *destination/source path*, not fixture content,
  so the content is always one of the files below.
- Seeding skips the core's URI validation (D16), so every URI here uses a scheme the
  core admits (`https`, or an adapter's `bear`, `obsidian`, ...); a made-up scheme
  would make the same graph unimportable through Settings and uncapturable.

### `graph-empty.json`

`{"schema":"ubilink.graph.v3","resources":[],"links":[]}`. R11's export/import
round trip empties the live graph with it (`seed_graph` with `replace: true`, i.e.
clear, then import this); `graph_stats`/the a11y counts must then read 0. Importing
it alone would change nothing: `import_json` merges.

### `graph-backlinks.json` / `graph-backlinks-newer.json` (R3)

One subject (`uri: "https://subject.example/note"`, also `capture-subject.json`'s
capture), three backlinks at **distinct**,
explicit link timestamps, and one decoy resource that is captured but **not**
linked to the subject (must never appear in the backlink list). Newest-first order
(what the a11y backlink list must show):

| file | newest → oldest (by uri) |
|---|---|
| `graph-backlinks.json` | `gamma.example/three`, `beta.example/two`, `alpha.example/one` |
| `graph-backlinks-newer.json` | `delta.example/four`, `gamma.example/three`, `beta.example/two`, `alpha.example/one` |

`graph-backlinks-newer.json` is `graph-backlinks.json` plus a fourth resource
(`delta.example/four`) linked to the subject at a timestamp newer than all three —
load it after the capture view has already shown the first three and reopened, and
Delta must appear first (R3's proof).

### `graph-5000.json` (R4, R5)

Exactly 5,000 resources, every `uri` unique, **no links** (R4/R5 exercise the
virtualised row list and the fuzzy filter, not graph edges — `graph-backlinks*.json`
covers the edge/recency case). Generated by `generate_graph_5000()` in
`scripts/probe.py`, seed `GRAPH_5000_SEED = 20261003`: resource `i` (1..5000) is
named `Resource 000i` at `https://fixture-000i.example.test/resource`, but its
`created_at` is a seeded shuffle of `i` — so the alphabetical order (by name, what
`list_resources` sorts on) and the recency order (by `created_at`, what
`list_resources_with_counts` sorts on) disagree, the way a real graph's do.
Regenerate with `python3 scripts/probe.py fixtures --generate`; never hand-edit it.

### `graph-ranking.json` (R5)

The corpus `ranking-golden.json`'s queries match against: 22 resources (no links),
each with a realistic `name` **and** `uri` (`"GitHub - ubilink"` /
`https://github.com/ubilink/ubilink`, `"Triage inbox notes"` /
`bear://x-callback-url/open-note?id=7f3a9c21`, ...). Most items' names and uris
both contain the same obvious text (a browser tab's title usually echoes its
domain), but a few deliberately don't: `r21` ("Triage inbox notes") has a title
that carries a match while its Bear uri is an opaque id, and `r22` ("Reddit
discussion", `https://rddt.example/thread/99231`) matches on both fields with
genuinely different spans — see the worked examples below.

### `ranking-golden.json` (R5)

A JSON **list** of exactly 20 entries:

```json
{ "query": "gthb",
  "expect_top3": ["https://github.com/ubilink/ubilink"],
  "decoys": ["https://gitlab.com/ubilink/ubilink-mirror"] }
```

- `query`: what the user types into the link-browser filter.
- `expect_top3`: 1–3 URIs from `graph-ranking.json`, **in the order the filter must
  rank them** — the a11y rows' top matches (in document order) must equal this list
  exactly (a `sequence` query with `mode: "prefix"` in a scenario). An entry is
  identified by its `uri` even though the match may have come from its `name`
  (`uri` is the corpus's unique key; `name` is not).
- `decoys`: at least one URI from `graph-ranking.json` that looks superficially
  related but **never matches at all, on either field** (not "ranks low" —
  absent from the filtered rows entirely, let alone the top 3).

#### The reference ranking rule (normative)

R5 says the filter must "rank in-order subsequence matches above other matches".
That alone under-specifies the order *among* several subsequence matches — which
is exactly what this table pins down. `rank(query, items)` in `scripts/probe.py`
is the rule, byte for byte; `--check` recomputes every golden query's ranking with
it and fails if `expect_top3` disagrees, so this table can never drift from the
rule it claims to follow. **A Phase 1 Rust implementation of the filter must
reproduce this rule's output for every query in this table** (it need not use the
same internal algorithm — a different data structure that provably yields the
same order is fine).

Matching both `name` and `uri` is not a convenience: controller ruling R-m
(Task 10 fix round 2) requires it for feature parity (B1) with the Tauri panel,
whose filter already searches `${name} ${uri}` case-insensitively
(`dist/browse-state.mjs`). A uri-only scorer would make the GPUI browser *worse*
than the one it replaces — a Bear note is found by its title, not its opaque
`bear://...?id=` uri, and the reverse holds for items whose name is generic but
whose uri is distinctive.

Rule, in order of precedence:

1. **Match text — both fields**: the resource's `name` and its `uri`, each
   case-folded independently (NFKC is not applied — these are identifiers and
   URIs, not prose). An item matches if `query` is an in-order (not necessarily
   contiguous) subsequence of **either** field. Non-matches on both fields are
   dropped — never ranked, however "close" they look.
2. **Primary key — minimum window span**: for whichever of the two fields gives
   the better result, the length of the SHORTEST contiguous substring of that
   field that still contains `query` as a subsequence, taken over every possible
   embedding (not just the first/greedy-leftmost one — see the `ab`/`aabb`
   worked example below, where they differ). Shorter span ranks first, and an
   item's OWN span is always the smaller of its name-span and uri-span (its
   worse field never matters once its better one is known).
3. **Tie-break 1 — earliest start**: among spans of equal minimum length
   (whether from the same field or a tie between an item's two fields), the one
   starting earlier ranks first.
4. **Tie-break 2 — field priority (name before uri)**: reached ONLY when a
   single item's own name-match and uri-match tie on both span and start — an
   edge case internal to one item, never a comparison between two different
   items. `name` wins the tie because a title is what a user reads; this does
   not mean `name` matches are ranked above `uri` matches in general (the
   `rddt` worked example below shows a tighter `uri` match outranking a looser
   `name` match on a DIFFERENT item).
5. **Tie-break 3 — none**: deliberately no word-boundary or prefix bonus beyond
   the above. This corpus does not need one, and leaving it out keeps the rule
   a short, ordered list of unambiguous numbers instead of a second scoring
   pass bolted on.
6. **Final tie-break — uri ascending**: the `uri` itself, case-folded,
   lexicographic. Not "corpus file order" — `graph-ranking.json`'s array order is
   not part of the contract, and a real implementation's own corpus order has no
   reason to match this fixture file's, so the rule must not depend on it.

Pseudocode (what `min_window_span` + `rank` in `scripts/probe.py` implement):

```
function min_window_span(query, text):
    # shortest [start, end) of text containing query as a subsequence,
    # earliest start among ties; None if query is not a subsequence of text.
    best = None
    for each position i in text where a leftmost subsequence match of query
            starting the search at i completes at some end index e:
        walk backward from e to find the LATEST start s such that
            text[s..e] still contains query as a subsequence
        candidate = (length = e - s + 1, start = s)
        best = candidate if best is None or candidate is shorter
                              (or equal length with an earlier start)
        resume the forward search at s + 1   # not at e — this is what makes
                                              # it the minimum window, not the
                                              # greedy-leftmost one
    return best

function rank(query, items):   # items = [(name, uri), ...]
    hits = []
    for (name, uri) in items:
        # This item's own winner: smaller span, then earlier start, then
        # field priority (name before uri) -- scoped to this one item only.
        candidates = []  # each: (span, start, field)  where field: name=0, uri=1
        name_window = min_window_span(lower(query), lower(name))
        if name_window is not None:
            candidates.append((name_window.length, name_window.start, 0))
        uri_window = min_window_span(lower(query), lower(uri))
        if uri_window is not None:
            candidates.append((uri_window.length, uri_window.start, 1))
        if candidates is empty:
            continue  # matches neither field
        (span, start, _field) = min(candidates)   # tuple order = rule precedence
        hits.append((span, start, lower(uri), uri))
    sort hits by (span, start, lower(uri))         # rules 2, 3, 6 (5 adds nothing)
    return [uri for (_, _, _, uri) in hits]
```

Worked examples:

| query | item | winning field & window | why |
|---|---|---|---|
| `gthb` | `r1`: name `"GitHub - ubilink"`, uri `https://github.com/ubilink/ubilink` | **name**, span 6, start 0 | `g`,`t`,`h`,`b` is a subsequence of `GitHub` (skipping `i`,`u`) in BOTH fields, but the name's match starts at index 0 (the field itself begins with `GitHub`) vs. the uri's match starting at index 8 (after `https://`) — same span (6), name wins on earlier start (rule 3). |
| `ab` | (pure strings, not a corpus item) `"ab"` vs. text `"aabb"` | span **2**, start 1 (`"ab"` at index 1–2) | The GREEDY-leftmost embedding (`a` at 0, `b` at 2) spans 3 characters (`"aab"`) — but a tighter embedding exists (`a` at 1, `b` at 2, span 2). `min_window_span` finds the true minimum (2), not the greedy one (3); this is exactly why `rank` cannot be built on `is_subsequence` alone. |
| `trgn` | `r21`: name `"Triage inbox notes"`, uri `bear://x-callback-url/open-note?id=7f3a9c21` | **name only** — span 9, start 0; the uri has no `g` at all, so it does not match at all | The title carries the only match (controller ruling R-m's required case): a Bear note's `bear://...?id=` uri is an opaque id, exactly like the real Tauri browser's parity requirement. |
| `rddt` | `r22`: name `"Reddit discussion"` (span 6, start 0), uri `https://rddt.example/thread/99231` (span **4**, start 8) vs. `r6`: name `"Reddit r/rust"` (span 6, start 0), uri `https://reddit.com/...` (span 6, start 8) | `r22` ranks first: its OWN winning field is its uri (span 4 < its own name's span 6) | Both items are genuine `name`-based matches on `"Reddit"` (span 6 each), but `r22`'s uri contains the literal substring `rddt` (span 4) — a tighter match on a DIFFERENT field of a DIFFERENT item, so `r22` as a whole outranks `r6` even though `r6`'s `name` would tie `r22`'s `name`. This is the case rule 2 exists for: an item's span is always its better field, and better-field spans are compared across items regardless of which field won. |

`scripts/test_probe.py` unit-tests `min_window_span` (including the
greedy-vs-minimum case above), `rank`'s field-OR logic and field-priority
tie-break, that `rank`'s result doesn't depend on the input order, and that
`--check` fails when the table disagrees with the scorer.

## Capture fixtures (R1, R2, R3)

`load_fixture {kind: "capture", path}` — what the automation build hands the
capture view instead of a live `osascript` capture. Two shapes, never mixed in one
file:

```json
// success (capture-ok.json, capture-delayed.json)
{ "name": "<title>", "uri": "<uri>", "app": "<frontmost app name>",
  "delay_ms": <optional integer, ms before the result is available> }

// failure (capture-failed.json)
{ "error": "<a sentence that says what failed AND what to do (U3)>" }
```

- `capture-ok.json`: no `delay_ms` — resolves immediately.
- `capture-delayed.json`: `delay_ms: 1000` exactly (spec R1's 1 s delay; its proof measures the
  `capturing` state rendering *before* this resolves, then the real data after).
- `capture-failed.json`: only `error`, no `name`/`uri`/`app`/`delay_ms`.
- `capture-subject.json` (R3): a success capture of `graph-backlinks*.json`'s subject
  (`https://subject.example/note`, "Subject Note"), so the capture view shows that
  resource's backlinks. Its uri must equal the subject's (`--check`).

## Permission fixtures (R9)

`load_fixture {kind: "permission", path}`, mirroring `app/src/permissions.rs`'s
`PermissionReport`:

```json
{ "accessibility": <bool>, "automation": "granted" | "denied" | "not_determined" }
```

- `permissions-two-missing.json`: both missing (`accessibility: false`,
  `automation` not `"granted"`) — onboarding must show exactly two steps.
- `permissions-all-granted.json`: both granted — the "flipped" state after `key r`
- `permissions-accessibility-missing.json`: Automation granted, Accessibility missing — capture-permission-route round 3 (a failed capture stays on capture)
  (Re-check) reloads this fixture.
- The pane each step opens comes from `app/src/permissions.rs::settings_pane_url`
  (`"accessibility"` / `"automation"`), not from the fixture.

## `adapters.json` (R10)

Not a `load_fixture` kind (settings reads its adapter list the same way
`ubilink-app`'s `list_plugins` does — `ubilink_core::AdapterRegistry::defaults()`,
embedded at compile time from `core/src/adapters.default.json` — there is
nothing for a probe to swap out). This file is the **expected** result of that
read with no `plugins-state.json` override, for a scenario's `expect`/`see` to
check Settings against; `--check` cross-validates it against
`core/src/adapters.default.json` directly so it can't drift. A JSON list,
sorted case-insensitively by `app` (matching `list_plugins`'s own sort):

```json
{ "app": "Bear", "builtin": false, "user_defined": false, "enabled": true, "scheme": "bear" }
```

`builtin: true` rows (`Finder`, `Safari`) can never be toggled off; the test for
R10 (every adapter togglable + persisted) runs against the other eight.

## `login-item-*.json` (R13)

`load_fixture {kind: "login_item", path}`: the login-item store the automation
build's launch-at-login seam (`desktop-gpui/src/login_item.rs`, spec D6, ruling R-o)
uses instead of `SMAppService.mainApp`, so no probe ever registers a real login item.

```json
{ "status": "not_registered",
  "on_register": "enabled" | "requires_approval" | "not_found",
  "explanation": "<sentence: what the status means and what to do>" }
```

- `status`: what the seam reports now. Every committed file starts `not_registered`.
- `on_register`: the status a register call moves it to; unregister always moves it
  to `not_registered`.
- `explanation`: required for `requires_approval` and `not_found` (the seam reports
  it with that status, the view shows it verbatim, U3); absent for `enabled`.
- `calls` is never committed: the seam writes the new `status` and appends
  `"register"`/`"unregister"` to `calls` in the instance's private copy, so the status
  survives a restart and a probe reads back which calls the view made.

| file | register leads to |
|---|---|
| `login-item-enabled.json` | `enabled` |
| `login-item-requires-approval.json` | `requires_approval`, with an explanation naming System Settings > General > Login Items |
| `login-item-not-found.json` | `not_found`, with an explanation saying to move the app to Applications |

## `accent-*.json` (D26)

`load_fixture {kind: "accent", path}`: the accent colour an automation build themes
with instead of `NSColor.controlAccentColor` (`desktop-gpui/src/theme/accent.rs`), so
a run does not depend on the host's System Settings > Appearance > Accent colour.
Loading one re-themes the open panel in place, through the same path the system's
colour-change notification takes. Release builds never read it.

```json
{ "accent": "#rrggbb" }
```

| file | accent |
|---|---|
| `accent-blue.json` | `#007aff`, the macOS default (blue / Multicolor) |
| `accent-orange.json` | `#f7821b`, an orange accent: white text fails AA on it |
